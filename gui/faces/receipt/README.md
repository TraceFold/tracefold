## The one discipline this face exists to hold

`glovrex/req/405 SS5` (frozen `SS605`) splits a receipt into an **attest layer** (facts, moved for nothing) and a **render layer** (derived from attest, adding nothing). This face's own code carries that split structurally:

- `toRecord({id, delta, receipt})` is the attest step. It reads the two membrane answers verbatim; every member that is absent, unread, or arrives as something other than a scalar becomes a named hole, never a silent drop (conformance conditions 1/2: every question gets an answer, and "unknown" is never silently omitted).
- `digestAgreement(record)` is a face-local decide step (the same kind of helper `faces/ledger`'s `budgetFor()` is) -- it compares two facts `toRecord()` already read and invents nothing new.
- `view()` and its section builders are the render step: a pure function of what `toRecord()`/`digestAgreement()`/`parts/src/seal-claim.mjs`'s `claimOf()` already produced (condition 5). There is no code path in the shipped source that reads `.sealed` off a raw payload -- the row's seal cell and the verify section's printed standing both read `claim.sealed`/`claim.mark`, the one decided answer, everywhere.

**Negative control performed, not just planted**: a `rawSealed: Boolean(receiptBody?.sealed)` field was added to `toRecord()`'s output for real, and `verifySection` was changed for real to trust `claim.sealed || record.rawSealed` and to print `record.rawSealed ? 'sealed' : claim.standing`. Against a receipt body carrying `sealed: true` (no verifier wired, basis exact), **three independent detectors fired red on the real shipped source**: the behavioural test ("a mischievous sealed:true in the wire payload changes nothing"), `tools/gate.mjs`'s `no-boolean-sealed-claim` source check (fired on the actual planted line, not an isolated string), and `tools/gate.mjs`'s own `seal-claim-mark-matches-standing` tree check (caught the row's mark and the printed text disagreeing -- "row draws structure/unsealed but the claim line says sealed"). The file was restored from a byte-for-byte backup, `cmp`/MD5 confirmed identical restore, and a second `node --test` pass confirmed green again (69/69).

## req/03 §5's three-part contract, one screen

Same screen, three sections, in the order req/03 §5 states them:

- **(a) permanent address**: the receipt's `anchor` field -- the one thing on this screen a third party could use to find this receipt without coming back through this window. A missing anchor is drawn as a named hole, never as blank.
- **(b) bytes, extracted**: `parts/src/serial.mjs`'s `serial()` -- the cut digest, its cut sentence, and its not-a-proof caveat, always together (the part itself has no mode that emits the characters alone), plus the digest in full and the algorithm.
- **(c) confirm without the issuer**: the seal claim (never a boolean, always through `claimOf()`), `parts/src/seal-claim.mjs`'s `portability()` (what a third party would need in hand), and the checkable claims -- `digestAgreement()` (this face's own addition: does the receipt's stated digest agree with the delta's own postcondition digest) plus `parts/src/checkable.mjs`'s five structural claims, run over the one record in an array. Claims that do not hold are shown in red, not filtered out -- the `receipt-mismatch` fixture exercises this for real (a genuine digest disagreement, not a planted test string), and the rendered claim reads "does not hold" with both digests named.

## The id problem, and the decision made about it

This face draws one record, not a list, so it needs to know *which* delta to read a receipt for -- and `mount(host, port, notices)` is frozen at three arguments everywhere in this tree's prose (req/02, req/03 §1). Rather than add a fourth positional argument (which no gate currently forbids for a real face, but which would break the one contract every other face, every req file, and every shell-side caller assumes), this face reads the id off `host.getAttribute('data-receipt-id')` -- an attribute on the very host element the shell already hands it, not a fact learned about the shell itself. A host with no such attribute draws the honest `NO_ID` state, tested (`test/receipt.test.mjs`: "mount with no data-receipt-id on the host draws the no-id state").

**2. The menu (#348 (2)).** This face declares no acts, so the menu it offers is `copy` and nothing else -- and on this screen that is not a consolation for having no acts, it is the act this face has been missing since it was written.
